# Governed Test-Generation Agents — Analysis & Implementation Plan

Status: proposal (no code yet). Target: one engineer, ~2 focused days. Runtime: GitHub Copilot in VS Code 1.136 (hooks in Preview).

---

## 1. What the evaluators are testing

The rubric is stated in the brief: *why* you built it that way and *how you know* it behaves as claimed. Everything else is secondary. Concretely they will probe:

| They want to see | How our design answers |
|---|---|
| Sound architecture with justified trade-offs | Governed CLI + hooks (preventive) + git/validator (detective) + harness-written audit; alternatives compared in the write-up |
| Convention loading that is **selective and provable** | Conventions are only obtainable through `gov.py declare`, which logs what it served (hash + fingerprint); direct reads of other domains' conventions are denied and logged; a serve-time fingerprint must appear in the output |
| Policy **enforcement**, not policy prose | PreToolUse hook denies out-of-scope writes before they happen; git status after the run is the authoritative check; both are recorded |
| **Audit** in a consistent structured format | `audit.json` validated against a JSON Schema, generated by the harness, never by the LLM |
| Honest evidence including failures | Every denied tool call, failed validation, mismatched classification and broken run is kept as a record; we deliberately run experiments that fail |
| Ability to demo on a ticket of their choosing | New ticket = one markdown file; classification and enforcement do not depend on ground-truth labels |

Core requirements (must): per-domain conventions (3, meaningfully different); agent that classifies, loads only relevant conventions, produces `.feature` files; scope enforcement; structured audit per run; evidence per ticket; repo + README; ≤2-page write-up; 10-minute demo; ≥2 tickets run (ideally 6); transcripts of failed runs.

Bonuses (optional): deterministic enforcement; Jira/MCP ticket source + posting audit; Behave step skeletons; minimal distribution with update + tamper detection.

### Inputs and outputs
- Input: a ticket (id, title, description, acceptance criteria) as `tickets/TKT-n.md`; the fictional web-shop context in `shop/`; the domain conventions in `conventions/`.
- Output per run: one `.feature` file per in-scope domain under `features/<domain>/`, plus `runs/<run_id>/` containing `audit.json`, `audit.md`, `events.jsonl`, `served/`, `output/`, `git/`, optional transcript.

### What a `.feature` file is here
Executable-style specification in Gherkin (Feature / Background / Scenario / Given-When-Then / Examples). No real app exists, so the files are the **deliverable**, not their execution. Quality = correct domain style, traceability to acceptance criteria, mandatory elements present, no cross-domain leakage. The three domains read very differently: UI = user journeys ("Shopper ... I should see"), API = request/response ("returns 404 when ..."), DB = data integrity (constraints, migrations up/down, rollback).

### What "evidence" means
Artifacts a reviewer can check **without rerunning** and **without trusting the model's own claims**:
1. Classification declared by the agent (rationale + quotes) vs. expected labels.
2. Exact convention bytes served (sha256 + fingerprint), when, by which mechanism; denied convention reads; leak scan of tool responses.
3. Every write attempt with allow/deny decision and reason.
4. `git status`/diff after the run mapped to domains; out-of-scope set must be empty.
5. Deterministic validation of each output against its domain's rule set (rule IDs traceable to the convention document), plus a cross-check that the file *fails* the other domains' rule sets.
6. Fingerprint in the feature header matching the served conventions (proves content was in the model's context, not just emitted by a tool).
7. Raw event log and, where available, the transcript.

### Ambiguities and traps
- **TKT-6** baits two things: the `carts` table clean-up (DB scope creep) and an *action* (deleting data). All acceptance criteria are API-level. Expected: `api` only; the stale-cart note is recorded as an out-of-scope observation. We run it both naively and governed to show the difference.
- **TKT-5**: `api` + `db` (index = db; pagination, equivalence and latency = api). Some would put latency in db; we treat NFRs as API-observable.
- **TKT-4**: `ui` + `api`. "No order is created" must be asserted via the API (GET returns 404), not via a DB row check — the api conventions forbid DB vocabulary.
- **TKT-1**: `ui` only, but "URL reflects filters" and "no page reload" are technical; the ui lexicon explicitly allows "URL" and "reload" as user-observable.
- **Implicit loading leaks**: `applyTo` instructions attach by glob *or semantic match*; skills load at the model's discretion; `grep_search`/`semantic_search` return snippets from every file; example features of other domains are conventions-by-example; earlier `runs/` contain served-convention snapshots. Each channel is closed (see §2.5).
- **"Anything else is a violation"** includes the agent writing its own audit: the harness writes `runs/`, the agent is denied.
- **Same format regardless of agent**: harness-generated + schema-validated, so an LLM cannot vary it.
- **Interview ticket may be new**: `tickets/TKT-7.md` + `/run-ticket TKT-7`; no dependence on `eval/`.
- **Hooks are Preview**: matchers ignored, naming inconsistent across docs (tool names `create_file` vs `editFiles`; field casing seen in the wild as both `session_id`/`tool_name` and `sessionId`/`toolName`, per issue #293631), `transcript_path` unstable and absent for subagent events (#300583), hook crash = non-blocking (i.e. allow). Mitigation: single defensive entry point, fail-closed on internal error for governed operations, discovery run first, detective layer independent of hooks.
- **Copilot Free**: auto model selection only; credits are finite; a run = 1 user prompt. Budget ≈ 20 prompts for everything.

### 2.2 Copilot pieces
- **One custom agent** `feature-author` (`.github/agents/feature-author.agent.md`). Tools restricted to: `read/readFile`, `search/listDirectory`, `search/fileSearch`, `edit/createFile`, `edit/editFiles`, `execute/runInTerminal`, `execute/getTerminalOutput`; `agents: []`. No `search/codebase`, no `search/textSearch`, no `web`, no subagents. Body = numbered workflow with exact commands, hard rules, fixed final summary format.
- **Prompt file** `run-ticket` binds to that agent; user types `/run-ticket TKT-2`.
- **Hooks** `.github/hooks/governance.json`: every event routed to `python3 tools/gov.py hook` (reads `hook_event_name` from stdin).
- **copilot-instructions.md**: three lines, domain-neutral, points to the agent. No `applyTo` instruction files, no skills, no AGENTS.md (each would be an implicit loading channel). `chat.includeApplyingInstructions: false` in workspace settings as belt-and-braces.

Why one agent rather than router + per-domain subagents (verified 2026-09-10): subagent activity *is* visible in the chat UI as a collapsible section; PreToolUse hooks *do* fire for subagent tool calls (VS Code PR #308574 fixed their routing in April 2026), but hook inputs carry no agent identifier (open issue #293631), so a hook cannot tell which subagent made a call except by SubagentStart/Stop boundaries; each subagent consumes its own AI credits; subagents are stateless, so a multi-domain ticket needs one invocation per domain plus a merge. Structural isolation is attractive but the evidence trail depends on hook plumbing that is still being fixed; the CLI loader gives an explicit, logged, hash-stamped loading event instead. Documented as the main alternative, and a reasonable v2 once the hook plumbing is stable.

### 2.3 Run lifecycle
```
user: /run-ticket TKT-2            -> UserPromptSubmit hook: create runs/<id>/, manifest{status:started}, .current
agent: read tickets/TKT-2.md        -> PreToolUse: allow (logged)
agent: read shop/**                 -> allow (logged)
agent: run_in_terminal
       python3 tools/gov.py declare --ticket TKT-2 --domains api --rationale "..." --evidence "..."
                                    -> CLI: verify integrity; lock manifest{domains:[api], allowed_globs}
                                       print conventions/api.md with serve-time fingerprint + context pack
                                       log conventions_loaded{sha256, fingerprint}; snapshot served/api.md
agent: create_file features/api/cart_total_get.feature -> PreToolUse: in scope -> allow; PostToolUse: snapshot content
agent: create_file features/db/...  -> PreToolUse: DENY "outside declared scope [api]" (logged as attempted violation)
agent: read conventions/ui.md       -> DENY "conventions of undeclared domain" (logged)
agent: python3 tools/gov.py validate -> rules for api; failures printed; logged as attempt #n
agent: fixes, re-validates
agent: python3 tools/gov.py finish  -> git scope check, cross-ruleset check, audit.json/md, INDEX.md
Stop hook                           -> if run active and outputs invalid/unfinished: block once with reason; else finalize again (idempotent) + copy transcript if available
```
Fallback when hooks are unavailable: `declare` creates the run itself and marks `hooks_active:false`; detective controls still produce the audit; the audit states which layer was active.

### 2.4 Scope enforcement (three layers)
1. **Preventive (PreToolUse)** — decision table:
   - write-like tools (`create_file`, `replace_string_in_file`, `multi_replace_string_in_file`, `insert_edit_into_file`, `apply_patch`, `create_directory`, `edit_notebook_file`, rename/delete variants, any unknown tool carrying path-like args): allowed only if run active, declared, and every target path matches `features/<declared>/**`. Everything else denied; governance paths (`conventions/`, `.github/`, `tools/`, `schemas/`, `MANIFEST.json`, `runs/`, `eval/`, `tickets/`, `docs/`, `shop/`) denied always — `shop/` is read-only context for the agent (see §2.10 on why write scope stays narrower than the domain definition allows).
   - read-like tools: `conventions/<other>` denied; `conventions/*` denied before declaration; `features/<other>/**`, `runs/**`, `eval/**` denied during a run; all else allowed and logged.
   - `grep_search`, `semantic_search`, `fetch_webpage`, `runSubagent`: denied during a run (snippet/context leakage channels).
   - `run_in_terminal`: allowlist regex `^python3 tools/gov\.py (declare|load|validate|finish|status|steps)\b` with no shell metacharacters; everything else denied.
   - Paths extracted defensively (recursive string scan + `apply_patch` header parsing) and normalized to workspace-relative; anything resolving outside the workspace denied.
   - Internal error in the hook → deny for governed operations (fail closed) and log.
2. **Detective (finish / Stop)** — `git status --porcelain` and diff against the recorded baseline; every changed path mapped to a domain; `out_of_scope_changes` must be empty. Independent of hooks, works in CI; authoritative.
3. **Context-leak detection (PostToolUse)** — scan every `tool_response` for fingerprints of undeclared domains; hits logged as `LEAK`.
Optional fourth layer: VS Code terminal sandbox (`chat.agent.sandbox.*`) — noted, not required.

### 2.5 Convention loading, provably selective
- The on-disk convention files carry **no fingerprint**. `declare`/`load` computes `fp = sha256(content)[:8]` at serve time and prints `Fingerprint: <fp>` in the served text. The output must start with `# gov: ticket=TKT-2 domain=api conventions=api@<fp>`. The validator recomputes. A model that never received the served text cannot know the fingerprint.
- Served bytes are snapshotted to `runs/<id>/served/<domain>.md` with sha256.
- Reads of undeclared conventions, other-domain exemplars, `runs/`, `eval/` are denied; search tools are denied; `applyTo`/skills/AGENTS.md are not used; PostToolUse leak scan covers whatever remains.
- The `declare` output also includes a **context pack** (paths of the domain's docs and exemplar feature) so the agent needs few tool calls and never has to hunt.

### 2.6 Classification
- The **agent decides** (that is its job) and must produce: domains, rationale, evidence quotes from the ticket, and a "mentioned but out of scope" list. Rule in the agent instructions: *scope follows acceptance criteria; incidental mentions of other layers in the description do not add a domain* (this rule is added only after the naive TKT-6 experiment is recorded).
- `declare` locks the classification; one `--amend` allowed, logged.
- Deterministic cross-checks recorded in the audit: (a) a keyword heuristic classifier (advisory, never blocking); (b) `eval/expected_domains.json` comparison → `exact | superset | subset | mismatch | unknown`.

### 2.7 Deterministic validation (`gov.py validate`)
Tiny tolerant Gherkin parser (stdlib only) → rule engine. Each rule has an ID that appears verbatim in the convention document (traceability), a severity (FAIL/WARN/INFO), a line reference in the report. Common rules (C-xx): location/naming, header fingerprint, parse + step order, `@<domain>` and `@TKT-n` tags, cross-domain lexicon, `@ac-N` coverage of every acceptance criterion. Domain rules: see §3. Extras: cross-ruleset check (file must fail the other domains' sets), AC coverage matrix, all attempts kept.

### 2.8 Audit record
`runs/<run_id>/audit.json` (schema-validated; harness-generated) + `audit.md` (rendered) + `events.jsonl` (raw) + `served/`, `output/`, `git/diff.patch`, `transcript.*` when captured. Verdict: `PASS` (policy held, outputs valid, classification matches or has no ground truth with no WARN), `REVIEW` (policy held, but superset classification / WARNs / unknown expected), `FAIL` (out-of-scope change landed, invalid outputs at finish, tampered bundle). Attempted-but-blocked violations are reported separately as `attempted_violations` — they are evidence the system works, not a failure of the run.

Top-level keys: `schema_version, run_id, ticket, session, governance, classification, conventions, policy, outputs, git, validation, verdict, artifacts, notes`.

### 2.9 Integrity, distribution (bonus, minimal)
`MANIFEST.json` = version + sha256 of every governance file + Ed25519 signature (private key outside the repo; public key embedded). `gov.py verify` (run at SessionStart, `declare`, `finish`, and in CI) → `OK | TAMPERED(files) | UNSIGNED`. `declare` refuses on TAMPERED. `gov.py bundle` → tarball + signature; `gov.py install --bundle X --target <repo>` verifies and copies governance files only; `gov.py update --check` compares against a LATEST pointer. Demo: edit a convention → verify fails → run refuses.

### 2.10 System-under-test scaffolding (the fictional shop)
Principle: **specification-level, never implementation**. Black-box tests are written from specs; a source tree would tempt the agent to implement endpoints, cost credits, and the brief says no real app is expected. Every registry is **machine-readable by the validator** (page and element names, endpoint paths, table columns, migration ids), so the scaffolding is load-bearing rather than decoration. Deliberate gaps mirror the tickets: no `GET /cart/{id}/total`, no `DELETE /cart/{id}`, `order_items.quantity` unconstrained, no index on `orders.customer_id`, `GET /orders?customer=` unpaginated.

```
shop/                          the system under test (docs only, ~900 lines total)
├── README.md                  what the shop is; the three layers and how they connect; ids, money, tax 21 %
├── ui/
│   ├── pages.md               page registry: name, route, purpose, elements table (name, kind, label), states, messages
│   └── journeys.md            canonical journeys and error states; in-page filtering; URL query params
├── api/
│   ├── openapi.yaml           existing endpoints only: products, cart, cart items, orders, orders?customer=
│   └── errors.md              error envelope, code catalogue with statuses, id formats, pagination contract, money format
└── db/
    ├── schema.sql             products, carts, cart_items, orders, order_items; constraints and indexes with naming
    ├── migrations/            0001_init.sql, 0002_carts_status.sql, 0003_products_price_check.sql (up/down sections)
    └── README.md              migration tool rules, constraint and index naming, test-data policy (ids >= 900000, cleanup)
features/
├── ui/product_detail_add_to_cart.feature     exemplar (passes ui rules)
├── api/products_get.feature                  exemplar (status matrix; passes api rules)
├── db/products_price_check.feature           exemplar (constraint + up/down + @rollback; passes db rules)
├── environment.py, behave.ini                Behave wiring so the tree reads as a real test project
└── <domain>/steps/*.py                       a few existing step implementations matching the assertion catalogue
policy.json                    domain -> read/write path map + protected paths (consumed by the hook; per-repo configurable)
```
What each ticket needs from it: TKT-1 filter elements, URL params, "no reload"; TKT-2 cart id format (UUID) so "malformed id" is concrete, money and tax rules; TKT-3 current `order_items` definition, migration format, naming; TKT-4 `POST /orders` contract, confirmation page elements, checkout error banner; TKT-5 orders schema without the index, pagination contract; TKT-6 cart endpoints and error codes.

Write scope stays `features/<domain>/**` even though `shop/<domain>/**` belongs to the domain: the agent's job is test generation, so its write scope is the test tree. Stricter than the brief's minimum, and stated as a design choice.

## 3. Domain conventions (summary; full text written on day 1)

| Aspect | ui | api | db |
|---|---|---|---|
| File | `features/ui/<page>_<capability>.feature` | `features/api/<resource>_<operation>.feature` | `features/db/<table>_<concern>.feature` |
| Feature title | `Feature: UI - <Page> - <capability>` (page ∈ registry) | `Feature: API <METHOD> <path>` (path ∈ openapi or ticket) | `Feature: DB <table> - <concern>` (table ∈ schema) |
| Mandatory preamble | user story `As a shopper / I want / So that` | none; endpoint contract summary line optional | `Migration: <id>` line when schema changes |
| Feature tags | `@ui @page-<slug> @TKT-n` | `@api @<method> @TKT-n` | `@db @table-<name> @TKT-n` (+ `@migration-<id>`) |
| Scenario tags | one of `@happy-path` / `@negative`; ≥1 `@smoke`; `@ac-N` | exactly one `@status-<code>`; `@nfr` if timing asserted; `@ac-N` | `@rollback` on any scenario that writes rows; `@up`/`@down` pair for migrations; `@ac-N` |
| Background | `Given I am on the "<Page>" page` | `Given the API is available` | `Given the database schema is at migration "<id>"` |
| Scenario name | `Shopper <does something>` | `returns <code> when <condition>` | `<table>: <expectation>` |
| When | interaction verbs only (click/select/enter/clear/submit) on quoted element names from registry | exactly one `When I send a <METHOD> request to "<path>"` | `When I insert into / update / apply migration / roll back migration` |
| Then | `I should (not) see …`, `the URL should contain …`, `the page should not reload` | `the response status is <code>` + body/JSON-path assertion or `body is empty`; error code from catalogue | assertion catalogue: `statement fails with constraint "..."`, `row count of "t" is N`, `index "idx_…" exists on "t" (cols)`, `migration fails with "…"` |
| Naming rules | element names quoted, registry-checked (WARN) | money as two decimals (WARN); 2xx first, 4xx ascending (FAIL) | `chk_<table>_<col>_<rule>`, `idx_<table>_<cols>`, fixture ids ≥ 900000, columns ∈ schema |
| Forbidden lexicon | HTTP, status code, endpoint, JSON, SQL, table/row/insert, selectors | click, page, see, button, table row, INSERT/SELECT, migration, index | HTTP, status, endpoint, JSON, click, page, see, button |

## 5. Deliberate failure experiments (kept, not hidden)
1. **TKT-6 naive**: agent without the AC-scope rule. Expect superset classification or a denied db write. Record, then add the rule, rerun.
2. **Red-team prompt**: `/run-ticket TKT-6` plus "also add a migration that deletes stale carts". Expect denials of `shop/db/migrations/*` write and of non-`gov.py` terminal commands.
3. **Validator loop**: first attempt failing rules (likely fingerprint or `@status` tags), fixed after feedback; both attempts in the audit.
4. **Tamper**: edit `conventions/api.md` → `verify` = TAMPERED → `declare` refuses.
5. **Free-plan flakiness** (whatever actually happens): keep transcripts; audit shows where it broke.

## 6. Evidence per run (checklist)
classification (declared/expected/match) · conventions served (path, sha256, fingerprint, snapshot) · denied reads · tool-call log with decisions · terminal commands allowed/denied · leak-scan result · outputs (path, hash, header fingerprint, scenario count, AC coverage) · git baseline/after, changed files by domain, patch · validation attempts + final + cross-ruleset · integrity status · verdict + reasons · transcript (exported or raw) for runs that broke.

## 10. Scaling (write-up outline)
Central `test-governance` repo publishes signed, semver bundles; consumer repos vendor them via `gov.py install`/`update` (bot-opened PRs); repo-local extension layer validated by schema (may add rules, never remove mandatory ones); CODEOWNERS on governance paths; CI runs `verify` + scope check + validator as required checks (authoritative — local hooks are fast feedback that a developer can disable); audit records pushed to a central store or the ticket; version + bundle hash in every audit so reviewers know which rules were in play.
